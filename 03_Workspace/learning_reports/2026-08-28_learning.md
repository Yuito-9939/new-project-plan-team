## 1. 今週のタスクで登場した専門用語と解説

| 用語 | 意味（初心者向け） |
|---|---|
| ハルシネーション | AIが「もっともらしい嘘」を作ってしまう現象。今週、WebSearchの要約が「SNS運用関連AIツール市場1,200億円・前年比32%成長」「PwC効果測定未実施59.8%」という具体的な数値を提示したが、原文をWebFetchで直接確認したところ、どちらの数値も記事中に一切存在しなかった（08/24）。まるで人が「あの本にこう書いてあったよ」と自信満々に話したのに、実際にその本を開いてみたら書かれていなかった、という状態に近い |
| 原典・一次情報 | 調査を実施した組織が直接公開している原文・原データ。今週の例では、東京商工リサーチ・帝国データバンク・商工中金の調査PDF/プレスリリース本文が該当する |
| 二次情報・要約 | 誰かが一次情報を紹介・要約した情報。検索エンジンの「AI要約」もこれにあたり、今週のように要約自体が不正確なことがある |
| WTP（Willingness to Pay、支払い意思） | 顧客が「実際にいくらまでなら払ってもよいと思っているか」という意欲のこと。今週の特命調査の核心テーマで、「AI自動化に失敗した中小企業は、外部の伴走支援に本当にお金を払うのか」を検証しようとした |
| 代替指標 | 本当に知りたい数値（今回は「挫折率」「解約率」）が見つからないときに、その代わりとして使える別の数値のこと。今週は「挫折率」そのものは見つからなかったが、商工中金の「AI活用を個人任せにしている企業64.9%」という数値を、"定着していない実態"を示す代替指標として採用した |
| 利害関係者ソース（要割引） | 調査を発表した組織自身が、その調査結果を使って自社サービスを売り込みたい立場にある場合、数値が良く見えるように偏る可能性があること。今週は、SNS運用支援会社自身が発表した調査（クロス・プロップワークス等）についてこの点を明記し、数値を鵜呑みにせず「要割引」として扱った |
| 景品表示法・優良誤認表示 | 商品やサービスの内容を実際より著しく良く見せる表示を禁じる法律とその違反類型。今週、AI生成のメニュー画像が実物と乖離して炎上した事例から、この論点が開発候補の一つとして浮上したが、法律の解釈はチームの専門外であり、専門家（弁護士等）への確認が必要な領域として切り分けた |
| 経営企画（05_Business）の兼務 | Report部門が週次レポートを作る際、事業性評価を専門とする経営企画部門の役割も一時的に担うこと（共通ルール4「他部門の仕事を行わない」の例外として、役割定義上明示的に認められている）。今回、Reportが3つの機能案それぞれについて「収益モデル・価格・採算・ROI・リスク」の表を埋めた |
| MVP（Minimum Viable Product、実用最小限の製品） | 最初から全部の機能を作るのではなく、「これだけあれば価値が試せる」という最小限の機能に絞って作ること。今週評価した3つの機能案のうち、どれを候補Aの最初のバージョン（MVP）に含めるかを議論した |

## 2. チームが行った判断と「なぜそう判断したか」

- **AI要約の数値を採用前に必ず原文照合する判断（08/24）**: WebSearchの要約に具体的な数値（市場1,200億円等）が出ても、原文をWebFetchで確認したところ記載が一切なかった。**判断基準**: 「数字が具体的で説得力があるほど、逆に慎重に裏取りする」という考え方。もっともらしい数字ほど検証せずに信じてしまいがちだが、それこそが危険信号だと捉える習慣が大切。
- **ピンポイント数値の代わりに代替指標を採用した判断（08/25）**: 「挫折率○%」という数字は官公庁一次資料を3日間探しても見つからなかった。そこで、意味的に近い「個人任せにしている企業64.9%」という数字を、"完全に同じではないが方向性を裏付ける代替指標"として採用した。**判断基準**: 欲しい数字がそのまま見つからないとき、「何も使えない」と諦めるのではなく、「これは何を示す数字なら使えるか」を考え直し、必ずその数字が何を意味していないか（挫折率そのものではない、等）も明記した上で使う。
- **法務に関わる開発候補を「見送り推奨」とした判断（今回の週次レポート）**: AI生成画像の品質ゲート＋景品表示法対応という候補について、技術的には作れそうに見えても、「優良誤認表示にあたるかどうか」の法解釈はチームの誰の専門でもないと判断した。**判断基準**: 共通ルール7「他部門の仕事を行わない」は部門間だけでなく、「そもそもチームの外（法律の専門家）に確認すべき領域かどうか」の線引きにも応用できる。自信がないまま進めるより、「ここから先は専門家の確認が必要」と正直に区切ることが安全。
- **3件の【開発候補】を新規事業ではなく「既存候補の機能拡張」と位置づけた判断（今回の週次レポート）**: 今週タグ付けされた3件は、いずれも前回すでに条件付きGoとした候補Aのターゲット層・課題と重なっていた。**判断基準**: 新しいアイデアが出てきたときに、それが本当に「新しい事業」なのか、「既存の取り組みの一部」なのかを見極めることで、評価の重複や過大な期待値を避けられる。今回は後者と判断し、無理に3つの独立事業として評価するのではなく、候補AのMVPに組み込むかどうかという実務的な問いに絞った。

## 3. 今週学んだことのまとめ

1. **AIの要約は「もっともらしい嘘」を混ぜることがある**: 今週、WebSearchのAI要約に登場した具体的な数値（市場規模・効果測定率）が、原文には存在しないことが複数回判明した。生成AIを使う際は、「見た目が自信満々で具体的な数字」ほど、採用前に必ず原典を確認するという習慣が欠かせない。
2. **「欲しいデータがない」ときの代替指標の使い方**: 挫折率・解約率という直接の数字が見つからなくても、「個人任せ64.9%」のような近い意味の数字を、意味を正確に説明した上で代替指標として使うことができる。ただし「これは挫折率そのものではない」と明記することが必須。
3. **無料の代替手段が有料機能の価値を奪うことがある**: 今週評価したROIダッシュボード機能は、Meta自身が同種の分析機能を無償提供し始めていることが分かり、有料での差別化が難しいかもしれないという結論になった。良いアイデアでも、大手プラットフォームが無料化すればビジネスとして成立しなくなるリスクがある。
4. **「守りの価値」（リスク回避）もビジネスになりうる**: AI生成画像の炎上事例から生まれた品質ゲートの提案は、「時短」ではなく「炎上・信用失墜を防ぐ」という守りの価値を持つ。ただし今回は法律の解釈という専門外の壁があり、進めるには専門家の確認が必要という結論になった。
5. **新しい発見を「新事業」と「既存事業の機能」に仕分けする視点**: 今週出てきた3つの開発候補は、実はすべて前回評価済みの候補Aの一部だった。新しい情報が出るたびに0から評価をやり直すのではなく、「これは既存の取り組みとどう関係するか」を最初に整理すると、無駄な重複評価を避けられる。

## 4. 復習した方がよい内容

- **原典確認（裏取り）の具体的なやり方**: 今週、WebSearchの要約とWebFetchでの原文確認で結果が食い違う場面が複数回あった。「検索結果の要約を見て終わり」にせず、「その要約のもとになったページを実際に開いて確認する」という一手間を、次回具体例で復習することを推奨する。
- **代替指標を使うときの書き方**: 「本来知りたい数字」と「代わりに使った数字」がズレていることを読み手に正確に伝える書き方（「挫折率ではなく、個人任せの比率」等）は、今回のレポートで実践したが、今後も繰り返し出てくる考え方なので、他のテーマでも練習するとよい。

## 5. 次に勉強すると良いこと（理由付き）

1. **景品表示法など、AIサービスに関わりやすい法律の基礎**: 今週、AI生成画像の品質ゲートという候補が「法務確認が必要」という理由で見送りになった。今後もAIを使ったサービスでは同様の壁に当たる可能性が高いため、優良誤認表示・薬機法など「AIで何かを作って見せる」ビジネスに関係しやすい法律の基礎を、専門家に相談する前の予備知識として押さえておくと判断が早くなる（優先度：中）。
2. **無料ツールとの差別化の考え方**: 今週、Meta公式の無償AI機能拡充によって、有料機能の価値が薄れるリスクが見えた。「大手プラットフォームがいつか無料化しそうな機能」と「大手が無料化しにくい機能（伴走・個別対応など）」を見分ける視点を、次のフェーズ（要件定義）に進む前に持っておくと、機能の優先順位付けがしやすくなる（優先度：高）。
3. **アンケート調査のサンプル数・実施年の見方の実践**: 今週もN=102（2021年、美容師限定）のような小規模・やや古いデータを「参考」として扱う場面があった。「このデータはどこまで一般化してよいか」を判断する練習を、実際のデータで繰り返すと精度が上がる（優先度：中、前回学習レポートからの継続テーマ）。

## 6. 学習ロードマップ上の現在地

- **これまで来た道**: リポジトリ立ち上げ → 経理・総務エージェント候補の調査 → SNS集客支援へのテーマ転換 → 候補Aの7軸評価・条件付きGo判断（08/21）→ 今回、特命調査（WTP検証）の完了と、候補Aの機能拡張案3件の評価、というところまで進んだ。
- **今いる場所**: 「候補Aを実際に作るとしたら、どの機能から手を付けるか」という、一次評価よりさらに一歩具体的な段階に入った。あわせて「AIの要約を鵜呑みにしない」「法律に関わる領域は専門家に確認する」という、AIを使ってビジネスを進める上での実務的な注意点を2つ、具体的な失敗事例とともに学んだ段階。
- **次に進む場所**: オーナーが今回の確認事項（3機能案のGo/NoGo、実地検証の実施可否）に回答した後、Goが確定した機能から、PM部門の企画書作成 → Architect部門の要件定義・設計、という開発フローの次フェーズに進む。特に候補A-3（品質ゲート）は専門家確認という新しい種類のステップを経る予定であり、「開発フローに法務確認が挟まる」初めての事例になる見込み。
