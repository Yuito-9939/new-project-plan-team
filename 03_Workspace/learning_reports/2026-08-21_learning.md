## 1. 今週のタスクで登場した専門用語と解説

| 用語 | 意味（初心者向け） |
|---|---|
| 一次情報 / 一次データ | 調査を実施した組織・企業が直接公開している原文・原データのこと。例えるなら「本人から直接聞いた話」。今週の場合、帝国データバンクやクロス・プロップワークスの調査PDF・プレスリリース本文が一次情報にあたる |
| 二次情報（WebSearch要約） | 誰かが一次情報を要約・紹介した情報。「人から聞いた話をさらに又聞きした話」に近い。検索エンジンの要約はこの二次情報にあたり、まれに要約自体が不正確なことがある（今週の「飲食店68%」の数値で実際に起きた） |
| 裏取り（要裏取り） | ある情報が本当に正しいか、元の資料に当たって確認する作業。ニュース記者が「本当にその情報は正しいか」を確認する作業と同じ |
| EGRESS_BLOCKED | この開発環境から外部サイトへの通信（WebFetch）が、ネットワークの出口（egress）でブロックされている状態を示すエラー。今週前半は5日連続で発生していたが、08/20に解消した |
| 7軸評価 | 難易度・開発コスト・学習コスト・保守性・将来性・AIとの相性・初心者へのおすすめ度の7つの物差しで、開発候補を多角的に評価する仕組み。1つの物差し（例：儲かるかどうか）だけで判断すると見落としが出るため、複数の視点を用意している |
| Go / NoGo（条件付き推奨） | 「進める（Go）」「やめる（NoGo）」のほかに、「ある条件を満たせば進めてよい（条件付き推奨）」という第三の選択肢。今回の候補は「価格を実際に試してみる小さな検証（PoC）をしてから本格開発に進む」という条件を付けた |
| PoC（Proof of Concept、概念実証） | 本格的に作り込む前に、小規模・低コストで「このアイデアは本当にうまくいきそうか」を試す検証のこと。今回は「数店舗に試験的に価格を提示してみる」といった規模の検証を想定している |
| 損益分岐点（採算の目安） | 売上とコストがちょうど釣り合う「これ以上ユーザーが増えれば黒字になる」というライン。今回の試算では「有料ユーザー約20人で損益分岐」という仮の数字を出したが、価格・コストの前提がすべて仮置きなので、あくまで考え方の練習用の数字である点に注意 |
| 収益モデル | どうやってお金を稼ぐかの型のこと。「月額サブスク」「買い切り」「従量課金」などがある。今回の候補は既存の代行サービスに合わせて月額サブスクを想定した |
| ブランチ・マージ（Git用語） | 作業内容を枝分かれ（ブランチ）させて別々に進め、あとで本流（main）に合流（マージ）させる仕組み。今週は、Research部門の2日分（08/18・08/21）の日次リサーチが枝分かれしたまま本流に合流していない状態が見つかった。作業自体は完了していたが「本棚（main）に本を戻し忘れていた」ような状態だった |

## 2. チームが行った判断と「なぜそう判断したか」

- **調査テーマを経理・総務からSNS集客支援へ切り替えた判断（08/17）**: 会計・経理領域は「金額を間違えると実害が出る」責任の重さがあり、現時点のチームのスキルではリスクが高いと判断した。一方SNS集客支援は失敗しても金銭的実害が経理ほど大きくなく、まずは実績を積みやすいという考え方が背景にある。**判断基準**: 「うまくいかなかったときの被害の大きさ」を軸に、リスクの小さい領域から着手する、という考え方は新規事業の初期選定でよく使われる基準。
- **一次データ（解約率・実支払い相場）の探索を途中で区切った判断（08/19・08/20）**: 何日も探しても見つからない情報を無限に探し続けると時間だけが失われる。「見つからない」こと自体も一つの調査結果（＝一次統計として世の中に公開されていない可能性が高い）と捉え、「ないものはない前提で次に進む」という判断をした。**判断基準**: 調査には終わりがないので、「あと何回探して見つからなければ次に進む」という区切りをあらかじめ決めておくと、判断に迷わなくなる。
- **候補Aを「条件付き推奨」とした判断（今回の週次レポート）**: 市場性（複数業種でニーズの手がかりあり）と技術（AIとの相性が高い）は前向きだが、採算（価格・解約率）の裏付けとなる一次データがゼロという状態だった。**判断基準**: 「市場性・技術・採算」の3つのうち1つでも根拠が弱い場合、いきなり「推奨」とはせず、弱い部分を補う小さな検証を条件にする、という考え方。全部そろってから動くと機会を逃すが、何も検証せずに大きく投資するとリスクが高すぎる、その中間を取る判断。
- **未マージの日次リサーチをそのまま反映した判断（今回のReport作業）**: 内容自体はResearch部門がすでに作成済みで、新しく調査をしたわけではなかったため、「新規調査（他部門の仕事）」ではなく「すでにある成果物を正しい場所に戻す」作業と判断した。ただし判断の余地がある行為だったため、実施したことをレポートに明記し、人間に確認を仰ぐ形にした。**判断基準**: ルールの範囲内か迷うときは、「やってよいか」だけで止まらず、「何をしたかを隠さず報告して、人間が後から検証・修正できる状態にしておく」ことが安全な進め方。

## 3. 今週学んだことのまとめ

1. **「導入率の高さ」と「成果実感」は別物**: SNSを「使っている」割合が高くても、「効果が出ている」割合は別に確認しないと、市場性を見誤る（飲食店82.6%活用 vs 小売の売上貢献実感16%など）。
2. **検索エンジンの要約だけに頼ると、出典自体が怪しい情報が混ざることがある**: 「飲食店68%が3ヶ月で更新停止」という数値は、日によって出典名が食い違い、3日連続で原文に到達できなかった。数字が具体的で説得力があるように見えても、出典を確認できるまでは採用しない、という慎重さが必要。
3. **「見つからない」も立派な調査結果**: 何かを探して見つからないとき、「探し方が悪い」と思い込んで無限に探し続けるのではなく、「公開されていない可能性が高い」という結論として扱い、次の判断（価格は仮置きで進める等）に活かすことができる。
4. **採算の数字は「仮置き」でも一度計算してみる価値がある**: 正確な数字がなくても、「もし月額1.5万円で固定費30万円なら20人で黒字」という試算を一度出してみることで、「この事業が成立するにはどれくらいの規模が必要か」の感覚がつかめる。ただし仮置きの数字を事実であるかのように扱わないことが重要。
5. **成果物が「作られたこと」と「正しい場所に届いていること」は別**: 今週、Research部門の2日分の作業は完了していたのに、mainブランチに反映されずに埋もれていた。作業を進めるだけでなく、「その成果がちゃんとチームの共有財産（main）になっているか」を定期的に確認する視点が必要。

## 4. 復習した方がよい内容

- **一次情報と二次情報の見分け方**: 今週、WebFetchのアクセス制限により一次情報に直接アクセスできない日が続き、Research部門が「WebSearch要約による」と明記する運用を徹底していた。この「情報の階層（一次・二次）を意識して、出典を明記する」という考え方は、今後どんな調査業務でも土台になるため、次回改めて具体例で復習することを推奨する。
- **損益分岐点の計算方法**: 今回の週次レポートで「固定費 ÷ 1人当たり粗利 ＝ 損益分岐点の人数」という簡単な式を使った。この式自体はシンプルだが、「固定費に何を含めるか」「粗利をどう見積もるか」の考え方は事業評価のたびに出てくるため、`estimate_template.md`（事業評価テンプレート）を使う次のフェーズで改めて練習するとよい。

## 5. 次に勉強すると良いこと（理由付き）

1. **Gitのブランチ・マージの基本操作**: 今週、日次リサーチが本流（main）に反映されていない事象が発生した。オーナー自身がこの仕組みを理解しておくと、「なぜ成果物が見当たらないのか」を自分でも確認できるようになる（育成視点での優先度：高）。
2. **簡易な事業性評価の考え方（損益分岐点・ROIの基礎）**: 次のフェーズ（Go判断後の事業評価書作成）に直結するため、「固定費・変動費・粗利」の基本用語だけでも先に押さえておくと、次回の事業評価書（`estimate_template.md`）を読んだときの理解が早くなる（優先度：中）。
3. **市場調査における「アンケート調査の母数・調査主体」の見方**: 今週、同じテーマの数値でも調査主体・母数によって数字が大きく異なることが繰り返し確認された（帝国データバンク40.5% vs 東京商工リサーチ54.8%など）。「その数値は誰が・何人に・いつ聞いたものか」を確認する習慣は、今後あらゆる調査結果を読むときに役立つ（優先度：中）。
