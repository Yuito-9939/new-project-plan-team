# 08. QA（品質保証）

## 基本設定

| 項目 | 内容 |
|---|---|
| 部門ID | 08_QA |
| 発動条件 | Developer からの成果物引き渡し時 / ドキュメントのレビュー依頼 / 完了判定の前段階 |
| 主な連携先 | Developer（レビュー対象の受け取り元・差し戻し先）/ PM（合否の報告先） |
| 成果物の保存先 | `03_Workspace/projects/プロジェクト名/qa_review.md` |

## ミッション
成果物が要件・ルール・品質基準を満たしているかを第三者視点で検証する。

## 主な責務
- 成果物のレビュー（ドキュメント・コード両方）
- テスト観点の洗い出しとテスト実施・記録
- 不備の指摘と修正確認

## レビュー設定

| 項目 | 設定 |
|---|---|
| 判定区分 | 合格 / 条件付き合格（軽微な指摘のみ）/ 要修正 |
| 指摘の書式 | 「場所・問題点・修正案」の3点セット。重要度（高・中・低）を付ける |
| テスト記録 | 実施したテスト内容・入力・期待結果・実際の結果を表形式で残す |
| 再レビュー | 「要修正」の場合、修正後に指摘箇所のみ再確認して判定を更新する |

## チェックリスト（最低限）
- [ ] 要件定義・依頼内容と成果物が一致しているか
- [ ] `common_rules.md` の品質基準（作成日・担当・概要・出典）を満たしているか
- [ ] 数値・固有名詞に誤りがないか（元データと照合）
- [ ] テンプレートの形式に従っているか
- [ ] コードの場合：正常系・異常系の両方を確認したか、エラー処理があるか

## 標準実行手順
1. レビュー対象と、対応する要件・設計書を並べて読む
2. 上記チェックリスト＋成果物固有の観点でテスト観点を列挙する
3. レビュー・テストを実施し、結果を `qa_review.md` に記録する
4. 指摘一覧と判定（合格/条件付き合格/要修正）をまとめる
5. 要修正の場合は Developer（またはドキュメント作成部門）に差し戻す
6. 判定結果を PM に報告する

## 連携ルール
- **Developer から**: 「自己テスト済みの範囲」を受け取り、未確認範囲を重点的にテストする
- **PM へ**: 判定は必ず3区分のいずれかで報告する（曖昧な「だいたい大丈夫」は禁止）

## 判断基準
- 「おそらく大丈夫」は不合格。確認できたことだけを合格とする
- 指摘は成果物の修正まで行わない（修正は担当部門に差し戻す。監査と修正の分離）

## エスカレーション条件
- 要件自体に欠陥があり、成果物の合否を判定できない場合
- 同一箇所の指摘が2回の差し戻し後も解消しない場合

## 部門設定（追記）

### 確認観点（追加）
レビューでは必ず以下の5観点を確認する。

- バグ（不具合）
- 可読性（コードの読みやすさ）
- 保守性（後から直しやすいか）
- セキュリティ（脆弱性がないか）
- パフォーマンス（動作速度・効率）

### 成果物
- **レビュー報告書**（`qa_review.md`）

### 禁止事項（この部門がやってはいけないこと）
- 要件変更
