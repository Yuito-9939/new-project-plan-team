# 開発フロー

## 1. 定常サイクル（自動稼働の基本）

このチームの目的は「世の中・中小企業・一般人が必要とする機能やシステム」を発見し、開発につなげることである。

```
[毎日]   Research がニーズ・トレンドを収集 → daily_research/ に保存
         有望なものに【開発候補】タグを付ける
[毎週金] Report が1週間分を集約 + 開発候補を評価
         （市場性 / 難易度 / 想定開発期間 / 想定販売価格・費用対効果）
         → weekly_reports/ に保存・報告
[人間]   週次レポートを見て Go / NoGo を判断する
[Go後]   企画書 → 市場調査 → 事業評価 → 要件定義・設計 → Claude Code が実装
         （下記のプロジェクト開発フローに接続）
[随時]   AI_Auditor の観点で自己チェック
```

## 2. プロジェクト開発フロー（新規案件が発生した場合）

| フェーズ | 担当部門 | 成果物（テンプレート） |
|---|---|---|
| 1. アイデア整理 | Orchestrator / PM | `idea_template.md` |
| 2. 市場調査 | Research（市場調査） | `research_template.md`（市場調査報告書） |
| 3. 事業性評価 | Business | `estimate_template.md` |
| 4. 要件定義 | Architect（システム設計）主担当・PM協力 | `requirements_template.md` |
| 5. 設計 | Architect | 設計書（requirements に追記可） |
| 6. 実装 | Developer | ソースコード・実装メモ |
| 7. 品質確認 | QA | テスト結果・レビュー記録 |
| 8. 報告 | Report | `report_template.md` |
| 9. 学習レポート・ナレッジ化 | Education | 学習レポート・手順書 |
| 10. 最終監査 | AI_Auditor | 監査コメント（報告に添付） |

- プロジェクト全体の管理情報は `project_template.md` を使い、`03_Workspace/projects/プロジェクト名/project.md` として管理する。
- フェーズを飛ばす場合は、その理由を成果物に明記する。

## 3. タスク実行の標準手順

1. リポジトリの最新状態を取得
2. `common_rules.md` → 本ファイル → 担当部門の `role.md` の順に読む
3. 作業計画を立てる（複数部門にまたがる場合は Orchestrator の役割定義に従い分解）
4. 作業を実行し、成果物をテンプレートに従って作成
5. `03_Workspace/` に保存し、コミット・プッシュ
6. AI_Auditor 観点のセルフチェック後、完了報告

## 4. エスカレーション基準

以下の場合は作業を中断し、状況を報告して人間の判断を仰ぐ：

- ルール同士が矛盾している場合
- 外部への送信・公開・課金を伴う操作が必要な場合
- 情報源の信頼性が確認できず、成果物の品質を保証できない場合
- 認証エラー等でリポジトリへの保存ができない場合（成果物は完了報告に全文添付する）
